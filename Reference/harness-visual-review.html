원문 설계안 최신 제안(응답 82)의 기본 정보는 PROJECT(프로젝트), TASK(작업), ASSET(재사용 자산), EVENT(발생 기록), RULE(규칙), PREVENTION(예방 지식)입니다. 아래는 여기에 실행 회차·승인·검증 근거 연결을 보완한 권고 모델입니다. 각 상자가 별도 프로그램이나 데이터베이스를 뜻하지는 않습니다.

작은 화면에서는 관계도를 좌우로 움직여 볼 수 있습니다. 각 상자는 키보드 Tab과 Enter로도 선택할 수 있습니다.

연결 규칙 1

이름보다 고유 번호로 연결

작업 번호 → 실행 번호 → 검증·근거 번호를 잇습니다. 같은 제목의 작업이나 여러 번의 시도가 섞이지 않게 합니다.

연결 규칙 2

현재 내용이 과거를 덮지 않게

TASK의 계획은 버전으로 관리하고, 실행 당시 버전을 RUN에 남깁니다. 이력은 덧붙여 보존하고 정정도 새 기록으로 남깁니다.

연결 규칙 3

보는 화면은 자동으로 계산

STATE(상태), DAG(선행관계도), 요약 LOG(이력)는 원본 기록을 읽어 만듭니다. 서로 다른 화면을 사람이 따로 수정하지 않습니다.

SSOT = Single Source of Truth, 기준이 되는 원본 정보. 원본을 한 파일에 모두 넣는다는 뜻으로 좁히지 않습니다. 현재 작업 계획의 원본과 과거 사실의 원본을 각각 정하고, 같은 사실을 여러 곳에서 따로 고치지 않는 것이 핵심입니다.

근거: 최신 응답 82의 PROJECT/TASK/ASSET/EVENT/RULE/PREVENTION 모델과 74의 중간 저장 설명. 초기 34·36의 AGENT/INCIDENT/LOG 목록을 그대로 확정 테이블로 합치지 않았습니다. RUN·APPROVAL·독립 VALIDATION·근거 연결은 이번 검토 권고이며 하위 기록으로 구현할 수도 있습니다.

한 작업을 따라가며 확인합니다

사용자가 보는 화면과 뒤에서 남는 기록을 나란히 봅니다. 실패 경로를 선택하면 복구와 예방규칙까지 이어집니다.

가상 예시 · 실제 실행 아님

“가상 학생의 주간 숙제계획표를 만들어 줘”

실제 개인정보 없이, 기존 예제 자료를 읽고 지정된 결과 폴더에 한글 표를 만드는 작업입니다.

사용자 화면의 최소 정보: 지금 하는 일, 실제 상태, 사용자가 할 일, 마지막 확인 결과, 다음 단계. 완료된 작업을 기준으로 진행률을 계산하고, 작업 완료율과 결과 전달 완료율을 따로 표시하는 것이 좋습니다.

중간에 꺼지면 어디서 다시 시작할까?

Checkpoint(중간 저장 지점)는 실행이 끝난 마지막 단계를 가리킵니다. Chunk(전달 묶음)는 사용자에게 결과를 보낸 단위를 가리킵니다. 두 번호를 구별해야 이미 한 작업을 다시 실행하지 않습니다.

같은 실패는 왜 계속 반복하지 않을까?

Fingerprint(실패 식별값)는 오류 종류·대상·단계·환경 등을 묶은 비교 표식입니다. 개별 발생은 실행 번호로 구별하고, 여러 작업·몇 달 뒤의 재사용은 정규화한 problem_pattern(공통 문제 유형)으로 찾습니다. 같은 실패가 반복되면 원인을 분석하고 새 조치가 없으면 재시도를 멈춥니다.

근거: 원문 응답 34·36의 작업·병목 흐름과 문자 깨짐 예시, 74의 중단·재개 및 전달 문제 보완. 예시 ID, 회차별 근거, 승인 버전 연결은 이번 검토 권고입니다.

역할은 나누되 프로그램은 작게 유지합니다

이름이 열두 개여도 상시 실행되는 에이전트 열두 개가 필요한 것은 아닙니다. 간단한 규칙과 스크립트로 처리할 일을 먼저 가려냅니다.

1. 현재 작업과 과거 실행의 원본을 나누기

계획이 바뀌어도 지난 실패·검증·승인 사실이 남습니까?

먼저 확정

원문에서 보이는 쟁점

초기안은 TASK에서 과거 LOG도 만든다고 설명합니다. 현재 TASK만으로 과거 사실을 복원할 수 없습니다. 최신 EVENT 모델을 이력 원본으로 구체화해야 합니다.

이번 검토 권고

TASK는 현재 운영 기준, EVENT·RUN·EVIDENCE는 과거 사실의 원본으로 둡니다. 승인도 작업 번호·계획 버전·대상·행동·범위에 묶고 중요한 변경 시 다시 판단합니다.

2. 쉬운 검사 합격이 필수 검사 면제는 아닙니다

한글·파일 형식이 맞으면 기능 시험을 건너뛰어도 됩니까?

필수 검사 유지

원문에서 보이는 쟁점

응답 82는 앞선 검사에서 확실히 합격하면 뒤의 불필요한 검사를 생략할 수 있다고 설명합니다. 이를 필수 기능 검사까지 생략하는 뜻으로 적용하면 위험합니다.

이번 검토 권고

변경 범위·위험·완료 기준에 따른 필수 검사는 모두 통과해야 합니다. 작업 상태와 검증 결과를 분리하고 PASS(합격)·FAIL(기준 미달)·ERROR(검사 오류)·NOT_RUN(미실행)을 구별합니다.

3. 담당자 한 명만으로 병렬 충돌이 사라지지는 않습니다

서로 다른 작업이 같은 파일이나 실행 자원을 쓰지는 않습니까?

독립성 확인

원문에서 보이는 쟁점

초기안은 잠금 장치를 제안하고, 후반 B 조사 보고는 충돌 없는 작업 배정과 상태 기록자 한 명을 강조합니다. 한 작업 한 담당자만으로 작업 간 충돌을 막지는 못합니다.

이번 검토 권고

선행관계·파일·기능 영역·공유 자원·권한을 실행 전에 검사합니다. 최소 구현은 충돌 없는 범위와 단일 상태 기록자로 시작하고, 실제 남는 문제에만 추가 동시성 제어를 적용합니다.

4. 복구와 예방에는 다음 실행의 증거가 필요합니다

한 번 성공한 해결을 어떤 조건에서 다시 적용할 수 있습니까?

재발·중복 방지

원문에서 보이는 쟁점

예방규칙과 재개 위치의 방향은 좋지만, 포인터 문자열이나 한 번의 성공만으로 장기 재사용과 안전한 복구가 증명되지는 않습니다.

이번 검토 권고

반복 가능한 문제 유형, 해결 근거, 적용 범위, 회귀 시험을 연결합니다. 중간 저장 뒤 재개해도 이미 처리한 부작용이 중복되지 않는지 확인합니다. 작업 저장과 결과 전달 번호를 분리합니다.

5. 비용과 완료 상태는 이름이 아니라 측정으로 판단합니다

“로컬이라 무료”, “Plugin이라 비쌈”, “표시가 PASS라 완료”라고 단정할 수 있습니까?

주장과 사실 구별

원문에서 보이는 쟁점

역할별 비용 순서는 실측되지 않은 가설입니다. 원격 도구 사례에서는 종료 실패 추정이 나중에 상태 검사기 오판으로 수정되었습니다.

이번 검토 권고

AI 호출 여부·입출력량·실행 시간·유지 비용을 측정합니다. Skill과 Hook도 AI를 부르면 토큰을 쓰며, Plugin이 대기 중이라는 사실만으로 토큰 비용을 단정할 수 없습니다. 완료 표시에 근거를 연결합니다.

설계 검토의 통과 조건: 위 다섯 항목에 대해 선택한 방식·근거·미해결 사항이 한 기준 문서에 정리되어 있어야 합니다. 문서가 길어졌다는 이유만으로 다음 구현 단계로 넘어가지 않습니다.

작게 검증하고 앱으로 넓힙니다

최신 대화의 범위를 따르면 핵심부 설계와 작은 시험이 먼저입니다. 아래 순서는 제안이며, 실제 구현 완료를 뜻하지 않습니다.
